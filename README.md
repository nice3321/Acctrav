نظام كامل لإدارة عمولات المبيعات والمالية التشغيلية: يستورد أرقام المبيعات، يحتسب
العمولات وفق سياسة معتمدة، يمرّرها في دورة اعتماد وصرف موثّقة، ويربطها بقائمة دخل
شهرية تشمل المصروفات والميزانيات.

## لماذا هذا النظام مبني بهذا الشكل

القاعدة الحاكمة: **المال لا يُحسب بأرقام عشرية عائمة، ولا يتغيّر بعد اعتماده.**

| القرار | السبب |
|---|---|
| كل المبالغ أعداد صحيحة بالهللة | `0.1 + 0.2 !== 0.3` غير مقبول في نظام رواتب. لا يوجد عمود `REAL` في المخطط كله |
| توزيع الوعاء بطريقة البواقي الكبرى | مجموع الحصص يساوي الوعاء **بالضبط** — لا تُخلق هللة ولا تضيع |
| تجميد الأرقام عند مغادرة المسودة | الدورة المعتمدة تحمل لقطة سياستها؛ تعديل السياسة لاحقًا لا يحرّك مبلغًا وقّع عليه إنسان |
| مفتاح `idempotency` على الصرف | نقرة مزدوجة أو مديران يضغطان معًا = تحويل واحد لا اثنان |
| التفويض في طبقة البيانات لا الواجهة | إخفاء زر ليس حماية؛ كل إجراء يسأل `requirePermission` من جديد |
| فصل المهام: المدير المالي لا يعتمد السياسة | لا يُصادق أحد على السياسة التي تحكم مكافآته |

## التشغيل

```bash
npm install
npm run setup     # ينشئ القاعدة ويبذر بيانات الشركة الفعلية
npm run dev
```

بيانات الدخول تُولَّد عشوائيًا وتُكتب في `credentials.local.txt` (غير مرفوع على Git).
كل حساب مُلزم بتغيير كلمة مروره عند أول دخول.

| السكربت | الوظيفة |
|---|---|
| `npm run dev` | تشغيل التطوير |
| `npm run setup` | ترحيلات + بذر البيانات |
| `npm run db:reset` | مسح وإعادة بناء القاعدة |
| `npm run verify` | فحص الأنواع + المدقق + الاختبارات + البناء |

## الأدوار والصلاحيات

| الدور | يرى | يعتمد | يصرف | يعدّل السياسة | يعتمد السياسة |
|---|---|---|---|---|---|
| المدير التنفيذي | الشركة | ✅ | ✅ | ✅ | ✅ |
| المدير المالي | الشركة | ✅ | ✅ | ✅ | ❌ |
| مدير المبيعات | الشركة | ❌ | ❌ | ❌ | ❌ |
| موظف مبيعات | كشفه فقط | ❌ | ❌ | ❌ | ❌ |

المصفوفة الكاملة في [`src/lib/rbac.ts`](src/lib/rbac.ts) — وهي المصدر الوحيد للصلاحيات
في النظام كله.

## دورة العمولة

```
مسودة ──► قيد المراجعة ──► معتمدة ──► مصروفة
  ▲            │              │
  └────────────┘              └──► ملغاة
```

الأرقام حيّة في **المسودة** فقط: أي تغيير في السياسة أو المبيعات يعيد احتسابها فورًا.
من **قيد المراجعة** فصاعدًا تُقرأ من لقطة محفوظة ولا يُعاد حسابها أبدًا.
**المصروفة نهائية** — التصحيح يكون بتسوية جديدة، لا بإعادة كتابة ما حُوِّل فعلًا.

## نموذجا الاحتساب

النموذج يُختار من **تاريخ الفترة**، لا من تاريخ اليوم:

**نظام الهدف الشهري** (من 2026-01-01): يجب أن يغطي ربح الشهر تكاليفه أولًا، ثم يُوزَّع
الفائض بنسبة المستوى المتحقق على فريق المبيعات — بوزن يمزج عدد الطلبات ونسبة المبيعات —
إضافة إلى حوافز الأقسام المؤثرة. وإن لم يتحقق الهدف تعمل **شبكة الأمان الفردية**: كل
موظف بلغ هدفه الشخصي يتقاضى نسبة من ربحه هو.

**نظام الشرائح** (ما قبل ذلك): شرائح تصاعدية على الربح المؤهل بعد خصم حصة الاستردادات.
ثابت لأن فترات الأرشيف صُرفت به فعلًا.

## البنية

```
src/lib/money.ts               حساب الهللات وتوزيع البواقي
src/lib/commission-engine.ts   المحرك — دوال نقية بلا حالة ولا قاعدة بيانات
src/lib/rbac.ts                الأدوار والصلاحيات وآلة حالة الدورة
src/lib/auth.ts                scrypt، الجلسات، حراس التفويض
src/lib/db.ts                  SQLite عبر node:sqlite + الترحيلات
src/lib/cycles.ts              طبقة القراءة والاحتساب
src/app/actions.ts             كل التعديلات المالية (Server Actions)
migrations/                    مخطط قاعدة البيانات
```

المحرك منفصل تمامًا عن قاعدة البيانات والواجهة — يأخذ صفوف مبيعات وسياسة، ويعيد نتيجة.
لذلك يمكن اختباره بالكامل دون تشغيل النظام.

## الأمان

- كلمات المرور بـ `scrypt` مع ملح لكل حساب — لا تُخزَّن ولا تُسجَّل بنصها الصريح
- جلسات في قاعدة البيانات بكوكي `httpOnly` + `SameSite=Lax`، صلاحية 12 ساعة
- إيقاف مؤقت بعد 8 محاولات فاشلة
- رسالة دخول موحّدة لا تكشف وجود الحساب من عدمه
- `proxy.ts` فحص مبدئي فقط؛ التفويض الحقيقي في كل إجراء خادمي
- سجل تدقيق غير قابل للحذف يسجّل الفاعل والمبلغ والسبب

**ملاحظة تشغيلية:** القاعدة ملف واحد على القرص. خذ نسخة من `data/acctrav.db` دوريًا —
هي كل شيء.
